## Instalación separada

La instalación anterior `/opt/pmcloud`, su nginx y sus cinco contenedores se conservan. La nueva utiliza `/opt/pmqms-demo/releases/d707210`, proyecto Compose `pmqmsdemo`, volúmenes propios y otro hostname. Los puertos 13000/18000/18080 se publican exclusivamente en loopback. PostgreSQL, SeaweedFS y ClamAV no tienen puertos públicos.

El override en `infrastructure/demo/compose.override.yml` se combina con el compose original sin eliminar servicios. Las imágenes API, web y PostgreSQL se construyeron para amd64 desde los Dockerfiles existentes; web requiere `--target runtime`. Los proveedores conservan los digests fijados en la fuente. El runtime API mantiene validación `production` para HTTPS y cookies, aunque todo el entorno y sus datos son de demostración. El bootstrap puntual usa `development` únicamente en la base separada `pmqms_demo`; rechaza otro destino.

API y web conservan filesystem readonly, `cap_drop: ALL`, `no-new-privileges` y límites de procesos. La cuenta PostgreSQL runtime no es superusuario ni tiene BYPASSRLS. Se confirmó migración `0049_tenant_suspension`. Los roles deben llamarse `pmcloud_app` y `pmcloud_migrator`, porque las migraciones existentes los referencian: no se modificaron migraciones para renombrarlos.

Certificado HTTPS emitido con el certbot existente y validación normal TLS. nginx mantiene inaccesibles `/admin` y `/realms/master/`; publica solo el realm del producto y los recursos necesarios. Las rutas QMS usan el proxy y su allowlist existentes. No se permiten credenciales en URLs ni se desactiva la comprobación de certificados.

Configuración privada fuera de Git: `/home/ubuntu/.config/pmqms-demo/demo.env`; storage config en `/opt/pmqms-demo/runtime`. No imprimir `docker compose config` sin filtrar, inspecciones de entorno completas, logs de autenticación ni claves. La guía con contraseñas existe solo en el equipo del usuario, con permisos 0600, fuera del repositorio y del servidor web.
