# QMS controls and implementation records

## Reference and scope

Odoo's `pm.qms.control` carries reusable objectives, purpose, rationale, implementation guidance and evidence guidance. A `pm.qms.control.instance` records a tenant's implementation against a process, with its own owner, applicability, dates and state. The SaaS keeps the catalog and implementation record separate and adapts company/organization alignment to tenant + unit + process scope.

Primary references: `addons/pm_qms_core/models/control.py`, `control_instance.py`, `activity.py` and `evidence_requirement.py`, plus `addons/pm_qms_evidence/models/evidence.py` and its `control_instance.py` extension in [Perfect-Match-QMS2026](https://github.com/Perfect-Match-Systems/Perfect-Match-QMS2026/tree/main/addons).

## Implemented

- Migration `0016_qms_controls` creates the tenant/unit/process-scoped control catalog and one implementation record per control/process. Composite foreign keys prevent cross-tenant and cross-unit relationships.
- Forced RLS protects both tables. QMS roles and purchased seats do not grant access. Exact capability grants are `controls.read`, `controls.manage`, `control_instances.read`, and `control_instances.manage`; auditors may receive read capabilities only. Control creation/state changes also require `processes.read` because their database integrity trigger checks the referenced process under RLS. Instance creation/transitions require `controls.read` so the active control is visible to the integrity trigger.
- Control workflow: draft → active → retired. Retired records are immutable; existing implementation records remain for traceability.
- Implementation workflow: not started → in progress → evidence required / under review → implemented; permitted returns from evidence required and review are checked in PostgreSQL. Not-applicable decisions require a reason. Implementation completion records the date.
- Migration `0017_ctrl_applicability` permits creation directly as not applicable only with a recorded justification.
- Migration `0018_control_definitions` adds reusable implementation activities and evidence requirements to control drafts. Activities retain sequence, objective, rationale, steps, success criteria, classification, readiness flag, role, output and evidence expectations. Requirements retain sequence, evidence type, mandatory status and reviewer acceptance criteria. Both definitions share the parent control's tenant, unit and process through composite foreign keys and forced RLS.
- Definition read uses the explicit control read/manage grant; writes require `controls.manage`. Database triggers enforce parent scope, immutable identity/definition keys and one-step row-version increments, and freeze definitions when their control is activated. Project-administration activities are excluded from readiness. Deactivation is soft and auditable; deletion is unavailable. Long narrative fields are hashed in audit.
- Row versions prevent stale overwrites. API audit events are written in the same transaction. Long guidance and notes are represented by SHA-256 in audit payloads; transition decisions are recorded with a 500-character limit.
- API endpoints: `/controls`, `/controls/{id}`, `/controls/{id}/activate`, `/controls/{id}/retire`, `/control-instances`, `/control-instances/{id}`, and `/control-instances/{id}/transition`.
- Definition endpoints: `GET/POST /controls/{id}/activities`, `PATCH /control-activities/{id}`, `GET/POST /controls/{id}/evidence-requirements`, and `PATCH /control-evidence-requirements/{id}`. Definitions can be added, edited or deactivated while their parent control is draft.
- Migration `0019_instance_activities` snapshots every active definition into a tenant-scoped activity task when an applicable implementation is created. Not-applicable records do not generate tasks. The snapshot preserves sequence, purpose, rationale, steps, success criteria, role, output and evidence expectations even if reference data later changes.
- Instance tasks have an owner, due date, notes and controlled status flow (`not_started` → `in_progress` → `blocked` / `under_review` → `completed`). Completion requires a summary and records the actor and timestamp. Every task mutation is versioned and audited in the same transaction; narrative audit fields use hashes. The database rejects direct status changes, completed-task edits, cross-tenant assignees and changes when the parent implementation is inactive.
- Required readiness tasks must be completed before an implementation may enter `under_review` or `implemented`. The API checks this and a PostgreSQL trigger enforces the same rule against direct writes. Administrative activities remain outside readiness.
- Task endpoints: `GET /control-instance-activities?instance_id=...`, `PATCH /control-instance-activities/{id}`, and `POST /control-instance-activities/{id}/transition`. The control workspace displays the task snapshot, status, responsible member, due date, success criteria, evidence expectations and completion summary.
- Migration `0020_control_evidence_review` snapshots every active evidence requirement into its implementation. Each item accepts a summary and optional link to an active, clean revision of a controlled document in the same tenant, unit and process; linking requires `documents.read`. Arbitrary object keys or external storage references are not accepted.
- Evidence workflow is draft → submitted → accepted/rejected. Rejected submissions can be corrected and resubmitted; accepted evidence is immutable. The reviewer must be a different active tenant member from the submitter and hold both `control_instances.manage` and the explicit `evidence.review` authority; read/navigation context additionally requires `controls.read` and `control_instances.read`. Review decision, reviewer and dates are audited; narrative content is hashed. Forced RLS, composite foreign keys, row versions and DB workflow guards protect scope and history.
- Every mandatory evidence item must be accepted before the implementation can enter `under_review` or `implemented`; the API and PostgreSQL both enforce this together with activity readiness. Optional evidence can be submitted and reviewed without blocking readiness.
- Evidence endpoints: `GET /control-instance-evidence?instance_id=...`, `PATCH /control-instance-evidence/{id}`, `POST /control-instance-evidence/{id}/submit`, and `POST /control-instance-evidence/{id}/review`. The control workspace supports summary entry, reviewer decisions, and selecting a released clean revision when the user has document read access.
- Web workspace supports scoped browsing, creating drafts, activation/retirement and creating/advancing implementation records. Drafts expose objective, description and all reusable Odoo guidance fields (purpose, rationale, implementation approach, steps, tools, evidence guidance and practical notes); guidance is readable from each control card. Draft edits include expected-version checks and are audited. Active definitions remain read-only in this initial UI.
- Control cards load reusable activities and evidence requirements on demand. Draft users with manage access can add or deactivate definitions; readers can review active definitions after activation. Each implementation now displays its generated, actionable activity tasks with assignment and due-date controls.

## Tested and pending

- PostgreSQL process/control integration: 185 passed in the complete suite. Includes tenant/process alignment, forced RLS, version conflicts, control and task workflows, evidence snapshots, mandatory evidence gating, submitter/reviewer separation, explicit review authority and audit history. Local OIDC E2E passed for generated tasks, evidence summary, a real PDF scanned and stored privately, independent document review/release, linkage of the released clean revision to evidence, self-review denial, independent evidence acceptance, readiness, same-origin proxy and audit. Temporary grants were revoked; test document was obsoleted; generated records use DEV-E2E identifiers.
- Migrations `0016`–`0020` upgrade and downgrade on disposable PostgreSQL. Downgrade across control/task/evidence audit events is rejected so history is not silently discarded.
- Backend Ruff and mypy pass. Frontend lint, typecheck and tests pass (8 tests across 6 files). Visual browser review remains pending; authenticated controls E2E passed through HTTP against the local OIDC/API/web runtime, not a visual browser walkthrough.
- Remaining Odoo-equivalence work includes end-to-end verification of controlled-document evidence links, external standard mappings, bulk rollout, richer process control/implementation visualization, and a visual browser walkthrough. This is a foundation, not full functional parity or an ISO/NIST certification claim.
